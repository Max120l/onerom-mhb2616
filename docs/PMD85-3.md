# The PMD 85-3 side: memory map, sockets, and the measurements that gate EXT mode

## Memory map

From MAME's `src/mame/tesla/pmd85.cpp`, which encodes the -3 precisely:

**Startup map** (in force from reset until the CPU's first I/O write):

| range | read | write |
|-------|------|-------|
| 0000–1FFF | ROM mirror | RAM |
| 2000–BFFF | ROM mirrors | RAM |
| C000–DFFF | ROM mirror | Video RAM #1 |
| E000–FFFF | ROM | Video RAM #2 |

The 8080 comes out of reset at 0x0000 and finds the monitor's first byte
there because the whole 64 KB reads as mirrored ROM. Reads and writes go to
*different* memories — a write-through arrangement, cleared as a whole by
the first OUT instruction.

**Normal map** (after the first I/O write):

| range | contents |
|-------|----------|
| 0000–BFFF | RAM |
| C000–DFFF | Video RAM #1 |
| E000–FFFF | ROM read / Video RAM #2 write |

Consequences for a board in a ROM socket:

- **The mirrors are the machine's doing, not the chips'.** The sockets see
  A0–A10 and their selects; whether the CPU address was 0x0005 or 0xE005 is
  the decoder's business. The board serves whatever it is strobed for and
  the mirror behaviour comes out right by construction.
- **The ROM is read during video scanout windows too** — E000–FFFF is shared
  with VRAM #2. Selects may therefore arrive denser than CPU instruction
  timing suggests. Irrelevant to correctness (the loop serves every cycle it
  is selected for), worth knowing when reading a scope trace.

## The four sockets

8 KB in four 2616s, one 2 KB window each, selects decoded from A11/A12 on
the mainboard. Established. What is *not* yet established, and must be
before EXT mode is trusted:

### Question 1: which pin carries the per-socket select

The textbook arrangement — and the default build's assumption — is /CE
(pin 18) decoded per socket, /OE (pin 20) common. But three arrangements
would all work for original chips:

| arrangement | pin 18 | pin 20 | EXT gates on |
|-------------|--------|--------|--------------|
| textbook | per-socket decode | common read strobe for the ROM region | /OE (`-DMHB_GATE_CE=OFF`) |
| inverted | common strobe | per-socket decode | /CE (`-DMHB_GATE_OE=OFF`) |
| both decoded | per-socket | per-socket | neither pin alone suffices — see below |

**The measurement:** machine running, original chips in place, scope on
pins 18 and 20 of one socket, trigger on falling edges.

- A pin that strobes at roughly *four times* the rate of the other, and
  strobes while code executing from *other* banks runs, is the **common**
  signal. Gate EXT on it.
- A pin that strobes only when this socket's own 2 KB is being fetched is
  the **per-socket** signal. EXT must not gate on it.
- If **both** pins are per-socket (both quiet while other banks run), no
  single-socket signal covers the region, and a third wire joins the two
  A11/A12 leads: bring the decoder's region-enable (or the OR of the four
  selects, or raw /MEMR qualified in firmware by address — pin 21's GPIO is
  free for exactly this if pin 21 turns out to be strapped to a rail). That
  is a firmware change too — file an issue against `mhb_select_masks`.

STATIC and HOTSPOT modes are immune to this question: a board answering for
one socket's 2 KB gates on both pins and is right under every arrangement.

### Question 2: which socket is which bank

Serving the monitor from the wrong socket order boots garbage that looks
like a dead machine. Settle it before EXT ever serves a monitor image:

1. Dump each original chip (or find per-chip images; the Infoserver archives
   monitor dumps per model).
2. `tools/rom_checksum.py pmd85-3.bin` gives the four reference bank sums;
   match each physical chip's dump to a bank by checksum.
3. Label the sockets. The board goes in any *one* of them in EXT mode — the
   two flying leads carry the bank, the socket only contributes power, bus
   and (per question 1) possibly the gate.

### Question 3: where to pick up A11 and A12

They exist at the decoder's inputs and at the CPU/bus buffers. Requirements
for the pick-up point: buffered (not the raw 8080 pins if an alternative
exists on the ROM side of the buffers), and stable by the time the select
asserts — which they are anywhere on the address bus proper, since the
decode *derives* from them. Two leads to the X1/X2 pads:

| lead | X pad | GPIO | index bit |
|------|-------|------|-----------|
| A11 | X1 | 9 | 1 |
| A12 | X2 | 8 | 0 |

The pads carry pull-downs, so a detached lead reads 0 — a board wired for
8 KB with a lead fallen off serves bank 0 for everything. The selftest
image makes that failure loud: every bank names itself in its own bytes, so
`check_selftest.py` on an in-circuit dump says "bank 0 pattern where bank 2
should be" rather than leaving it to symptom-guessing.

## The bring-up ladder

Each rung is cheap and rules out a class of fault before the next spends
time on it. The 1801RE2 project's lesson, imported wholesale: instrument
first, monitor image last.

1. **Bench, no machine.** Selftest image, STATIC mode, bank by jumpers.
   Read the board through a ROM reader as if it were a 2716.
   `check_selftest.py` must come back clean for all four jumper settings.
2. **Machine, STATIC, selftest.** Board in a socket *with the machine's
   original for that socket removed*, machine on. The monitor will fail its
   ROM test and stop — expected; the board's LED should show serving
   (steady flicker). This proves selects, levels and timing in-circuit
   without trusting contents.
3. **Machine, STATIC, real bank.** Monitor image for that one socket's
   bank. The machine should boot exactly as stock. This is the first rung
   with a working machine on it, and it is already a useful product — a
   2616 replacement.
4. **Machine, EXT, selftest → monitor.** Other three chips out, two leads
   on, gating per question 1. Selftest first (dump in-circuit if a reader
   arrangement allows, or probe), then the monitor. ROM test pass on the
   -3's own startup screen is the acceptance test — the machine checks its
   own checksum, which is a better instrument than anything external.
