# The PMD 85-3 side: memory map, socket wiring, and what remains to establish

## Memory map

From MAME's `src/mame/tesla/pmd85.cpp`, which encodes the -3 precisely:

**Startup map** (in force from reset until the first write to the system
8255 at F4-F7):

| range | read | write |
|-------|------|-------|
| 0000–1FFF | ROM mirror | RAM |
| 2000–BFFF | ROM mirrors | RAM |
| C000–DFFF | ROM mirror | Video RAM #1 |
| E000–FFFF | ROM | Video RAM #2 |

The 8080 comes out of reset at 0x0000 and finds the monitor's first byte
there because the whole 64 KB reads as mirrored ROM. Reads and writes go to
*different* memories — a write-through arrangement, cleared as a whole by
the first write to that 8255.

**Normal map** (after the first write to the system 8255, with PC4 high):

| range | contents |
|-------|----------|
| 0000–BFFF | RAM |
| C000–DFFF | Video RAM #1 |
| E000–FFFF | ROM read / Video RAM #2 write |

**AllRAM map** (PC4 low) — RAM across all 64 KB. **There is no ROM in the
machine at all.**

That third map is not a curiosity, and missing it cost three firmware
builds and two misdiagnosed bench sessions. The ROM/RAM choice is PC4 of
the system 8255 at F4–F7 (`GPMD85Emulator/src/SystemPIO.cpp`,
`WritePaging()`: `pg & 16` → ROM/RAM, else AllRAM; `pg & 32` → ROM
everywhere). And `OUT F7h` with bit 7 set is an 8255 **mode set**, which
clears every port C output latch as a side effect — so it drops PC4 and
takes the ROM out of the address space.

The monitor's own reset path is the proof, and it is worth reading closely:

```
E0A3: LHLD E0B3h    ┐ copy the four bytes at E0B3..E0B6 out of ROM
E0A6: SHLD E0B3h    │ and into RAM at the same addresses -- reads come
E0A9: LHLD E0B5h    │ from ROM and writes go to RAM, so copying a byte
E0AC: SHLD E0B5h    ┘ to where it already is moves it between them
E0AF: MVI A,82h
E0B1: OUT F7h       ← mode set: PC4 drops, the ROM leaves the machine
E0B3: MVI A,09h     ← these four bytes are fetched from RAM
E0B5: OUT F7h       ← BSR sets PC4: the ROM is back
E0B7: JMP E00Ah
```

That self-modifying preamble is load-bearing. For four instruction bytes
the machine has no ROM, and the monitor carries execution across the gap on
a RAM trampoline it built moments earlier.

**So a served image must never issue `OUT F7h` with bit 7 set from ROM.**
To clear the startup map without losing the ROM, write to **port A (F4h)**
instead: any write to that 8255 clears the mirror, and port A leaves port C
— and therefore PC4, and therefore the ROM — alone. Port A is an input
until something configures it otherwise, so the byte lands in a latch that
drives nothing, which makes it the most harmless write the machine accepts.

Consequences for a board in a ROM socket:

- **The mirrors are the machine's doing, not the chips'.** The sockets see
  A0–A10 and their selects; whether the CPU address was 0x0005 or 0xE005 is
  the decoder's business. The board serves whatever it is strobed for and
  the mirror behaviour comes out right by construction.
- **The ROM shares E000–FFFF with VRAM #2 writes**, so selects may arrive
  denser than CPU instruction timing suggests. Irrelevant to correctness
  (the loop serves every cycle it is selected for), worth knowing when
  reading a scope trace.
- **`/CS` going inactive and staying there is not a fault.** In AllRAM the
  machine stops addressing the ROM socket entirely, so a board that reports
  "select went away" is reporting the truth. This was read as a hardware
  problem for a whole bench session.

## The socket wiring — measured from the schematic

DOSKA CPU, 1 PK 280 77. Sockets DS4 (E), DS5 (D), DS6 (C), DS7 (B) — the
schematic prints DS6's letter as "0", but the real machine says C; the
sheet carries a few such typos, which is itself worth knowing — all
wired identically for address and data (JEDEC 2716 positions), with:

| signal | pin | wiring |
|--------|-----|--------|
| /CS | 20 | **pair select, active low**: DS4+DS5 share one net, DS6+DS7 the other |
| PR | 18 | **A11**: straight into DS4 and DS6, inverted into DS5 and DS7 |
| pin 21 | 21 | +5 V rail, with pin 24 |

This answers what used to be this file's question 1, and better than any of
the guessed arrangements: the socket hands the board a genuine address bit
(A11 on PR) *and* a half-decoded select (/CS covering a 4 KB pair). From
one socket the board therefore knows everything except which pair an access
to the *other* pair belongs to — and that is exactly one flying lead away.

What the wiring means for each firmware mode:

| mode | wires | gate | bank bits |
|------|-------|------|-----------|
| STATIC | 0 | /CS low AND PR at this chip's level | fixed |
| PAIR | 0 | /CS low | A11 = PR (± invert) |
| FULL8K | 1 | /CS low OR X1 low | A12 = which select; A11 = PR |
| HOTSPOT | 0 | /CS low AND PR at this chip's level | magic reads |

The FULL8K lead runs from the *other* pair's pin 20 (either empty socket of
that pair) to the board's X1 pad. X1 is pulled up on the board, so a
detached lead reads "other pair not selected" and the board degrades to
serving its own pair rather than serving wrong data.

## Still to establish

### 1. Which pair and which PR sense is which bank — SETTLED

The schematic fixed the *structure* (pairs, A11 polarity per socket); the
Infoserver's ROM archive fixed the *assignment*. Its per-chip `.bin`
files match the combined `monit3B.rom` byte-for-byte at these offsets —
not read off a table, but verified by comparing every byte:

| socket | letter | bank | monitor offset | CPU address | `MHB_SOCKET_PAIR` | `MHB_PR_INVERT` |
|--------|--------|------|----------------|-------------|-------------------|-----------------|
| DS4 | E | 0 | 0x0000–0x07FF | E000–E7FF | 0 | OFF |
| DS5 | D | 1 | 0x0800–0x0FFF | E800–EFFF | 0 | ON |
| DS6 | C | 2 | 0x1000–0x17FF | F000–F7FF | 1 | OFF |
| DS7 | B | 3 | 0x1800–0x1FFF | F800–FFFF | 1 | ON |

(`MHB_SOCKET_BANK` for STATIC/HOTSPOT is the bank column.) The letters
descend E→B as addresses ascend, matching the archive's own note that the
chips sit "in order E-D-C-B from the microprocessor" — DS4 nearest the
CPU. Two corollaries fall out:

- **The chips are selected when PR reads low.** DS4 holds bank 0
  (A11 = 0) and its PR is straight A11, so its select level is low — and
  the inverted sockets agree. This is also why MHB 2716 substitutions
  historically worked: the 2716's /CE lands on PR and is active low too.
- **The board's `MHB_PR_INVERT` is a pure socket property** (ON exactly
  for DS5/DS7), since the firmware's bank bit is A11 itself, not the
  chip's select sense.

If a boot ever contradicts this table, re-check the build switches before
doubting it: pairs swapped → wrong half executes, ROM test fails
immediately → `MHB_SOCKET_PAIR`. Banks within a pair swapped →
`MHB_PR_INVERT`. Do not reorder the image to compensate.

**Which reference image.** Monitor versions are not interchangeable;
the -3B machine wants `monit3B.rom`. Reference points (whole-file and
per-bank CRC32, banks 0..3), computed from the Infoserver archive
(`PMD85-rom-files`, RM-TEAM 2017):

| image | whole-file | bank 0 | bank 1 | bank 2 | bank 3 |
|-------|-----------|--------|--------|--------|--------|
| `monit3.rom` (plain -3; byte-identical to MAME's `pmd85-3.bin`) | `83E22C47` | `C443BE75` | `4EE6CE97` | `0C1E3552` | `83E9522F` |
| `monit3B.rom` (-3B) | `878F08DF` | `0A41D057` | `4EE6CE97` | `0C1E3552` | `9A7BBA86` |

The two versions differ **only in banks 0 and 3** (chips E and B): per
the archive's notes, 3B's ROLL/ROLL2/WRCHAR/ERASE routines avoid the SP
register, plus the compatibility-mode routine at FB64h. Service
consequence: C and D chips interchange freely between a -3 and a -3B;
E and B do not.

For machines with readable chips, the dump-based route remains in the
tools: `rom_checksum.py --identify ref.rom dump.bin` names a chip's bank
even from a degraded dump (mismatch counts against all four banks are
printed, so a marginal verdict looks marginal), and one identified chip
fixes all four sockets by XOR: pair-mate `b^1`, other pair `b^2`/`b^3`.
Do not substitute PMD 85-1 dumps for any of this — the -1 monitor is a
different 4 KB program and resembles no -3 bank.

**All four chips bad?** The cleanest case, not the worst: the board
serves everything (FULL8K, or two PAIR boards), the table above supplies
the mapping, and the machine's own startup ROM test is the confirmation.
Nothing left on the bus to fight, nothing to version-match against.

**Mixing sources when some chips are bad:** decide per bank where its
bytes come from. Serving the reference image for *all* banks (PAIR or
FULL8K) is the safe default — the monitor is one program, and its banks
cross-call, so a version mismatch between a surviving original chip and a
reference-served neighbour is a real (if unlikely) hazard. Before leaving
a good original in its socket next to reference-served banks, `--compare`
its dump against the reference: byte-identical means same version, mix
freely; differences mean find the matching version on the Infoserver or
serve all four banks from the board.

### 2. Is /CS qualified by the read strobe?

The original chips drive their outputs whenever /CS+PR select them, so
either /CS is qualified by /MEMR (asserts only on reads) or the machine
tolerates ROM outputs during write cycles into the mirrored region by
never letting decoded ROM selects and write strobes coincide. The original
chips' survival proves the arrangement is safe for *chip-shaped* behaviour
— and the firmware gates exactly as the chips do, so it inherits that
safety. Nothing to change; worth one scope glance at pin 20 against /WR
during the startup-map phase if anything ever looks off.

### 3. Serving beyond the monitor

The -3 also takes ROM cartridges through the ROM module interface (8255,
not in the CPU address space) — out of scope here; a cartridge is its own
project. HOTSPOT mode plus custom software is this project's answer for
"more than 8 KB", per docs/ROADMAP.md.

## The bring-up ladder

Each rung is cheap and rules out a class of fault before the next spends
time on it. Instrument first, monitor image last.

**Rung zero is not on the ladder, and it is not optional: Vcc, clock,
reset, with a meter and a scope.** Every diagnostic in this project
reports through a ROM being fetched, so all of them can only prove things
*downstream* of a running processor — the three preconditions of running
are exactly what no served image can ever test. This machine's own
history makes the point: its 8224 clock generator was dead, ten seconds
of probing found it, and the fanciest ladder in this repo would have
reported precisely nothing. Always start at the basics; the beacons begin
where the scope leaves off.

1. **Bench, no machine.** Selftest image, STATIC mode with
   `-DMHB_STATIC_IGNORE_PR=ON` and `-DMHB_SOCKET_BANK=<n>`, read through a
   2716 programmer (which parks PR at one level — that is what IGNORE_PR is
   for). `check_selftest.py` must come back clean for all four bank
   settings. Never take an IGNORE_PR build near a machine.
2. **Machine, STATIC, selftest.** Board in one socket, *that socket's
   original removed*, machine on. The monitor fails its ROM test and stops
   — expected; the board's LED must show serving (steady flicker). This
   proves selects, levels and timing in-circuit without trusting contents.
3. **Machine, STATIC, real bank.** The socket's own bank of the monitor
   image, `MHB_SOCKET_BANK`/`MHB_PR_INVERT` per the checksum table from
   question 1. The machine boots exactly as stock: the first genuinely
   useful configuration — a 2616 replacement.
4. **Machine, PAIR.** Pair-mate removed too, `MHB_SOCKET_PAIR` set, same
   image. Boot as stock proves the PR-as-A11 serving live. Two chips
   replaced, zero wires.
5. **Machine, FULL8K.** All four originals out, one lead from the other
   pair's pin 20 to X1. Boot as stock, ROM test pass on the -3's own
   startup screen — the machine checks its own checksum, which is a better
   instrument than anything external.

## Reading a machine that does not boot

The PMD 85-3's video hardware runs from its own counters, so **sync and a
screen full of uninitialised character tiles prove nothing about the
CPU** — that is what the display looks like whenever the processor is not
running the monitor, whatever the reason. The board's own status light is
the better instrument, and `-DMHB_DIAG=ON` makes it a specific one.

The ordinary status light says whether selects are arriving:

| light | meaning |
|-------|---------|
| green / flickering | selects arriving, the machine is reading us |
| **a brief flicker, then steady red** | the machine read us a few times and **stopped** |
| steady red from the start | nothing is selecting the board at all |

That middle case is the informative one, and it is not a board fault by
itself: an 8080 fed a byte it cannot execute sensibly can land on `HLT`
(0x76), after which it fetches nothing ever again. The bus goes quiet,
the board correctly reports "nobody is asking", and the screen keeps
showing whatever was in video RAM. **A processor that stopped and a board
that stopped look identical from outside** — hence the coverage frame.

`-DMHB_DIAG=ON` replaces the status light with a four-pulse frame, one
pulse per bank, latched since power-on: long green = this bank has been
read, short red = never read. It separates the candidates in one glance:

| frame | reading |
|-------|---------|
| all four green | every bank is being served; the fault is not coverage |
| 0,1 green — 2,3 red | the X1 lead is not delivering the other pair's select |
| only one green | PR is not moving, or the pair select is stuck |
| all red | the board is never selected: socket, /CS, or power |

A frame that differs between repeats means the machine got further that
time, which is itself worth knowing. (The first frame is sampled within
microseconds of boot, before the machine has been let out of reset, so
an all-red first frame followed by a populated second one is normal.)

### The frame is history, not present state

Latched since power-on and repeating every few seconds, while the machine
does everything it will ever do in the first few milliseconds. So the
normal reading on a machine that crashes is: nothing, then a fully
populated frame that keeps repeating **after the CPU has already halted
and the selects have gone quiet**. That is the instrument working, not a
contradiction — it is reporting what happened during the burst.

Two things follow, and the second is the one that matters:

- **Coverage proves the path, not the program.** All four banks green
  says the board *can* serve every bank and the machine *did* ask for
  every bank. It says nothing about whether the bytes were the right
  ones — a processor executing garbage wanders widely, and lights banks
  for the wrong reasons.
- **A short burst is itself a measurement.** A correct mapping leaves the
  monitor running indefinitely, so the selects never stop. Activity that
  stops after a burst means the processor stopped, and an 8080 stops for
  exactly one reason it can reach by accident: it fetched a `HLT` (0x76)
  out of bytes that were never meant to be executed in that order.

### The frame locates the board, not just the fault

**All four banks green proves which pair the board is sitting in**, which
is worth more than it looks. Banks 2 and 3 can only be driven when the X1
lead reads low *while the socket's own /CS reads high* — so an all-green
frame proves the lead is on a genuinely different select net from the
socket's own. Tap X1 from a socket of the other pair and get all four
banks, and the board is provably in the pair that lead did *not* come
from.

That collapses the remaining unknowns from four to one. The socket's pair
is settled by the frame; only the PR sense is left, and it is the
difference between the two sockets of that pair — the one taking straight
A11 and the one taking it inverted. One rebuild with `MHB_PR_INVERT`
flipped covers it.

## Testing a machine that cannot test itself

`tools/make_ramtest.py` builds an 8 KB image that runs a **March C-** over
the machine's RAM and reports through the ROM socket. Serve it with **`-DMHB_DIAG=3`** for the verdict lamp -- one colour, no
counting:

| lamp | the last completed pass said |
|------|------------------------------|
| green | RAM clean |
| red | hard fault: cells fail even read back immediately |
| blue | march fault only: they take data but do not **hold** it (refresh) |
| yellow | running; no pass has finished yet (~20 s each) |
| white | the program never ran |

The long colour is the **last completed pass**; the short blip after it is
the same verdict over **every** pass since power-on. So an intermittent
fault that is behaving right now still shows red or blue in the blip --
and, just as important, a fault that has been *fixed* turns the blip green
again after a power cycle rather than leaving a latched accusation on
screen forever.

This replaced a twenty-four-pulse frame that was misread twice, both times
producing patterns the ROM cannot physically emit (beacon 1 dark between a
lit 0 and 2; beacon 15 lit with all its detail bits dark). A frame nobody
can read is not a measurement, however much information it theoretically
contains -- and 25 seconds of long-versus-short pulses is not readable.
`-DMHB_DIAG=4` still blinks the full detail when a specific bit mask is
actually wanted:

| beacon | meaning |
|--------|---------|
| 0 | the processor executed from this image |
| 1 | the startup mirror map is cleared; RAM is readable |
| 2 | a whole March C- pass finished |
| 3 | **RAM fault** |
| 4-11 | which data bits D0-D7 ever read back wrong |
| 12-14 | which third of RAM the faults were in |
| 15 | **hard fault**: cells fail even when read back immediately |
| 16-23 | which bits failed that immediate read-back |

**Beacon 15 is the control that decides what a fault means.** March C-
writes a cell and comes back for it a whole sweep later; the immediate
read-back writes and reads microseconds apart. So:

| 3 | 15 | reading |
|---|----|---------|
| dark | dark | RAM is good |
| lit | lit | the cells or their data path are genuinely broken |
| lit | **dark** | the cells accept and return data but do not **hold** it — dynamic RAM that is not being refreshed. A refresh fault, not a memory fault; replacing the chips would fix nothing |

That last row is why the control exists. Without it a stopped refresh
circuit reads as "every chip bad", and someone spends a weekend replacing
perfectly good DRAM. The emulator test suite asserts this case
specifically: simulated cells that decay must light 3 and leave 15 dark.

A healthy machine lights 0, 1 and 2 and nothing else, forever. It also
paints video RAM with a stripe pattern, so a working display shows the
program is alive without anyone reading the LED.

Two things make it usable on a machine that cannot run its own monitor:

- **It never touches RAM.** No stack, no `CALL`, no `PUSH`, no interrupts;
  every branch is a jump and every variable is a register. A test that
  needed a stack would be standing on the thing it is testing. A unit test
  walks the compiled image instruction by instruction and fails if a single
  stack opcode appears.
- **It reports through the socket it is read from.** Reading a reserved ROM
  address is a *beacon*; the board sees the read and lights a bit. No video,
  no keyboard, no serial port needed — the machine talks through the chip
  it is executing.

March C- rather than a write-everything-then-check pass, because ten
operations per cell catch what one pass cannot: *transition* faults (a cell
that will not go 0→1 or 1→0) since every cell is read in both states after
being driven to them, and *coupling* faults since the array is walked both
up and down — a coupling that hides on the way up is exposed coming down.
A final address-uniqueness pass with an `H xor L` pattern covers the
decoder, which uniform 0s and 1s test weakly.

The image is verified in an 8080 emulator (`tools/i8080emu.py`) before it
is ever trusted: clean RAM must report clean, and simulated stuck bits,
whole dead chips and faults in each third must each be reported correctly.
The sibling project's lesson stands — the instrument is wrong more often
than the machine is surprising.

## Checking the processor before believing anything about memory

Every test above assumes the processor works. That assumption is free to
make and expensive to be wrong about: a marginal CPU, or a marginal bus
driver between it and the ROM, produces exactly the erratic behaviour that
gets blamed on memory. `tools/make_diag.py` builds an 8 KB image that
climbs a ladder instead, each rung standing only on the rungs below it.
Serve it with **`-DMHB_DIAG=5`**.

| rung | tests |
|------|-------|
| 0 | **alive** — the processor fetched, decoded and executed at all |
| 1 | registers: `MVI` to each, `MOV` between them, `CPI` |
| 2 | ALU and the Z/S/CY/P flags it sets |
| 3 | all eight conditional jumps, taken **and** not taken |
| 4 | 16-bit: `LXI INX DCX DAD`, including a carry across the byte |
| 5 | **data bus** — 256 ROM bytes covering every bit pattern; this is the path through the 8228, and it names the exact data lines that are wrong |
| 6 | ROM sum — all 8192 bytes, catching address-line faults a 256-byte table steps straight over |
| 7 | **I/O** — `OUT F4h`, clearing the startup mirror map |
| 8 | RAM — March C− plus the immediate read-back control |

Rungs 0–6 are the processor and the ROM path and nothing else: no writes,
no RAM reads, no I/O. The machine's first port write is a rung of its own
because it is the most hardware-dependent thing the ladder does, and it has
no business sitting below the rungs that prove the CPU can execute at all.
An earlier version cleared the mirror map inside rung 0, so a machine whose
port write went nowhere reported *"the processor never got past its first
instruction"* — true, and pointing at the wrong part. Rung 7 now proves the
map actually switched: it writes to `0000` and reads back, and reading the
ROM's own `C3` there means the `OUT` did not take.

Rung 7 writes to **F4h and not the F7h the monitor uses**, for the reason
in the memory-map section above: `OUT F7h` with bit 7 set is a mode set,
and a mode set takes the ROM out of the machine. A ladder whose job is to
reach RAM has no business risking that; the io stage does it deliberately,
last, with a trampoline.

The lamp reports the ladder as a count:

| lamp | meaning |
|------|---------|
| green, steady | every rung passed |
| red × (N+1) | rung N **failed** |
| blue × (N+1) | rung N started and never finished — it **hung** there |
| white × 1 | the program never ran (also the normal transient while the machine is still in reset) |

Blue matters as much as red. A processor that stops mid-rung reports
nothing at all, and *"it hung in rung 2"* is a different fault from *"rung
2 said no"*.

Every frame opens with a long **magenta** marker — a colour the lamp never
uses for data — and the count follows as short flashes. That is not
decoration. The first version relied on flash length and gap length alone,
and the count came back unreadable in practice; a frame you cannot count is
not a measurement, which is the same lesson the 24-pulse beacon frame
taught earlier on this machine.

### When the processor passes and the machine still stops

`--stage io` builds a second nine-rung image for exactly that case. It
drops rungs 1–6, which have by then been proved, and spends all nine rungs
on what is left: **one kind of bus cycle per rung**, ordered by what each
depends on.

| rung | the cycle it completes |
|------|------------------------|
| 0 | alive |
| 1 | a memory **write** — still mirrored, so a write and nothing else. Rungs 0–6 of the cpu stage are all reads, so this is the machine's first write of any kind |
| 2 | a memory **read** at a low address — still mirrored, so served from ROM: exercises the cycle and the low address bus with no DRAM cell involved |
| 3 | **the startup map clears** — `OUT F4h`, which leaves port C and therefore the ROM alone |
| 4 | **RAM actually holds data** — rung 1's byte, read back at last. Reading `C3` means the mirror never cleared and the ROM is still answering |
| 5 | RAM, March C− with the immediate read-back control |
| 6 | **video RAM** — `C000`–`DFFF`, the one region arbitrated against the display circuit. It writes a ramp, so a screen with sync shows the pattern |
| 7 | **the monitor's paging dance** — mode set, RAM trampoline, BSR |
| 8 | **came back from it** — the ROM is in the map again |

The order is the design. Rung 7 is the one step that cannot be made safe,
because for four instruction bytes there is no ROM in the machine; so it
goes last, after the processor, the bus, the ports, RAM and the video path
have all already reported. If the machine dies there it dies having told us
everything else is sound, which makes it a fact about the paging latch
rather than a mystery. Rung 8 exists only to say it came back.

An 8080 cannot fall over on a bad instruction — it can only stall waiting
for `READY`, or sit in `HOLD`. So on this image a **blue** count is not a
vague "it stopped somewhere": it names a bus cycle that never completed,
which is specific enough to put a probe on.

### When nothing clears the startup map

`--stage map` answers one question and only one: **which write, if any,
takes this machine out of the mirrored map?** It exists because `OUT F4h`
did not, on this machine, although `GPMD85Emulator` says any write to the
system 8255 should. Either the real trigger is narrower than that model or
the latch is stuck — and if it is stuck, the monitor cannot reach RAM
either, which would be the whole fault rather than a detail of it.

| rung | the write it tries |
|------|--------------------|
| 0 | alive |
| 1 | leaves `5A` at `0000` to recognise RAM by |
| 2 | **any I/O write at all** — `OUT 00h`, an undecoded port |
| 3 | 8255 **port A**, `F4h` |
| 4 | 8255 **port B**, `F5h` |
| 5 | 8255 **port C**, `F6h` (writing `10h`, so PC4's latch stays set) |
| 6 | 8255 **control register**, BSR set PC4 — a control-register write that does *not* clear the latches |
| 7 | a **read** of the 8255, `IN F6h` |
| 8 | none of them worked |

**Reporting is inverted in this stage, and only in this stage: the rung
that "fails" is the rung that worked.** Red × (N+1) names the write that
cleared the mirror; red ×9 means nothing did; blue keeps its ordinary
meaning of a cycle that never completed. Sharing the existing lamp beats
inventing a seventh way to blink at somebody, and the inversion is
harmless as long as it is written down — which is what this paragraph is
for.

**Red ×9 is what a healthy machine reports, and reading it as a fault cost
a day.** At reset port C of the 8255 is an *input*, so PC5 — the bit
`WritePaging()` decodes as "ROM only" — is undriven and the mirror stands.
Port A and port B writes do not touch port C. A BSR sets a latch but
leaves the pin undriven, so it never reaches the decoder. Not one of the
six candidates can clear the mirror on a machine in perfect health; only a
**mode set** can, because only a mode set makes port C an output. The
sweep is still worth running — it rules out six things in one flash — but
its negative result is not evidence of a fault.

### The one sequence that does work

`--stage paging` does what the monitor does, and nothing else. It is worth
running only once the 8228 is cleared, because it deliberately takes the
ROM out of the machine for three instruction bytes.

| rung | what it establishes |
|------|---------------------|
| 0 | alive |
| 1 | builds the trampoline in RAM, blind — reads come from ROM, so it cannot be checked first, and the monitor takes the same gamble at `E0A3` |
| 2 | the mode set: PC4 and PC5 both fall, the ROM leaves the address space |
| 3 | **came back** — the three RAM-resident bytes executed and put the ROM back |
| 4 | the mirror is finally gone (`0000` no longer answers `C3`) |
| 5 | RAM holds what rung 1 wrote there |
| 6 | RAM, March C− |
| 7 | video RAM |

The window is three bytes rather than four because `B` is loaded with the
BSR word beforehand, so it needs only `MOV A,B` instead of `MVI A,09h`.
Every cell that has to be right is a cell that can be wrong.

Three outcomes, all decisive:

| lamp | reading |
|------|---------|
| **blue ×3** | died in the ROM-less window: the trampoline never came back, so RAM cannot be **read**. The monitor cannot boot either, for exactly this reason |
| **red ×5** | survived, but `0000` still answers `C3` — the mirror really is stuck, and the 8255 is not what holds it |
| **green** | the machine is fine |

While the march runs — twenty-odd seconds over 48 KB — the lamp shows
**blue ×7**, which is the honest report of "rung 6 started, not yet
finished". It is a transient, not a verdict; wait for the frame after it.

On the bench this stage went green on the machine that started this whole
investigation, after a year of failed boots: trampoline executed, mirror
cleared, full march clean, video RAM clean. One green pass on a machine
with an intermittent history is evidence, not acquittal — that is what the
soak build of the RAM tester is for.

The port C candidate writes `10h` rather than `00h` on purpose. PC4 is
what holds the ROM in the address space, and clearing that latch is the
mistake the whole io stage exists because of.

### Everything proved so far is a read

That is worth stopping on. The cpu stage's rungs are all reads; the io
stage's write was never read back, because the mirror never cleared; the
port writes completed as *instructions* but nothing observable followed.
A machine whose 8228 never asserts a write strobe — `WO` (status D1) stuck
high kills `/MEMW` and `/IOW` together — behaves exactly like this, with
the stuck map as a symptom rather than the fault.

Two stages separate those, and the first needs no instrument at all.

**`--stage vram`** paints video RAM in a loop with a pattern that *moves*.
Video RAM is the one memory read by something other than the CPU, so it
reports without needing a single RAM read — which matters on a machine
that cannot perform one. A still pattern would be indistinguishable from
power-on garbage; nothing in a dead machine animates.

| screen | reading |
|--------|---------|
| crawls | memory writes work; the fault is the paging latch |
| static | this machine cannot write to memory, and nothing else matters |

**`--stage strobe-{iow,memw,memr}`** hammers one kind of bus cycle in a
tight loop — 32 cycles, then about 1.9 ms of quiet, forever. The envelope
is the measurement: a uniform stream of activity is hard to attribute to
anything, burst-and-silence is not. Four marker reads at the top of each
burst land on the *other* socket pair, so `/CS` on DS6/7 is a hardware
trigger for the burst that follows.

`memr` is the control, and it is the one stage whose envelope does **not**
appear — every instruction fetch is a memory read, so `/MEMR` streams
through the gap too. What it establishes is the probe: if `/MEMR` cannot
be found, nothing measured on the other two means anything. Run it first,
expect a uniform stream, and move on.

Relevant 8228 pins: **24 `/MEMR`, 25 `/IOR`, 26 `/MEMW`, 27 `/IOW`.**

On timing: the first version of this stage nested two 256-iteration delay
loops without multiplying them out, and fired its marker every 480 ms —
which at any timebase that resolves a 100 µs burst is indistinguishable
from a machine doing nothing, and cost a bench session. A test now bounds
the marker period in instructions.

## The test card

`tools/make_screentest.py` is the last diagnostic in the family and the
first with a display: everything earlier reported through an LED because
the screen could not be trusted, and this one reports through the screen
because now it can. Serve it with **`-DMHB_DIAG=3`** and the verdict lamp
runs alongside as a second channel (the beacons are
`make_ramtest.py`-compatible).

The card, top to bottom:

| element | what it tests |
|---------|---------------|
| 1-px border, all four sides | overscan and centering |
| title | — |
| gradient band | 6 dither densities × all 4 attributes. On a stock -3 that is bright / dim / blinking bright / blinking dim — a brightness ramp and a blink test at once; on a colour-modified machine, four colour bars |
| 24 px × 12-line crosshatch | geometry, linearity |
| progress bar | the running March C−, one segment per element, refilling live each pass |
| HARD row, D0–D7 boxes | bits that failed the immediate write/read-back control |
| MARCH row, D0–D7 boxes | bits that ever failed the march proper |
| PASS / FAIL | last pass's verdict; FAIL is drawn in the blinking attribute |
| tick line | one tick per pass: steady = clean, blinking = that pass failed. Forty to a line, then it clears |

The march covers `0000`–`BFFF` — everything except the video RAM it is
drawing on, whose test is the picture itself, including the write-only
half at `E000`–`FFFF`. Init is the proven paging trampoline; if the
mirror never clears, the card paints FAIL and parks, because writes reach
RAM even under the mirror and so even that verdict is visible.

It keeps the family discipline — no stack, no interrupts, every branch a
jump — and adds two rules of its own, both forced by the hardware: every
paint is a blind whole-byte store, because the frame's lower half cannot
be read back; and the two bytes of cross-pass state (pass counter, hard
bits) live in the invisible 16-byte margin each 64-byte line carries
beyond its 48 visible bytes, where the march never walks.
